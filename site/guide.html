Integration guide

A conversation layer for your site.

Run these commands from a Concourse checkout using Bun 1.4.3.

Concourse has two parts: a browser component on your static publication and an authenticated, same-origin API. The browser never decides who may read or write.

1. Prepare the backend.

Configure a site origin, managed login audience, and explicit membership. Apply all reviewed migrations through 0003_management.sql before deploying the Worker with its D1 binding. Route /__concourse/* to the Worker. Protect that path with Cloudflare Access before enabling the browser component.

Documentation can remain public. Private publications must protect all content, including assets, search indexes, downloads, production origins, and previews. Follow the backend deployment procedure for the reviewed infrastructure and database steps, and see the hosting guide.

2. Install in Hugo.

bun install --frozen-lockfile
bun run build:browser
bun src/cli/install-hugo.ts /path/to/your/site

Call the installed partial from your base or footer template with the current page as its context: {{ partial "concourse.html" . }}. Configure your Hugo parameters:

params:
  concourse:
    enabled: true
    site: your-site
    api: /__concourse/
    feedback: true

Use stable authored heading IDs. Hugo supplies the source path as the resource and hashes its raw content for the revision. Documentor also supports installation through publish.site.concourse.

Or add it to static HTML.

Run bun run build:browser from the Concourse checkout. Copy dist/concourse.js and dist/concourse.css to your site's /concourse/ directory. Place this marker outside the authored content. Use a stable resource name and a revision derived from your content. Put authored content in a main or article element, with unique IDs on h2–h4 headings. Concourse prefers main .content when present.

<div data-concourse data-site="your-site"
  data-resource="guide.html" data-revision="CONTENT_SHA256"
  data-api="/__concourse/" data-css="/concourse/concourse.css"
  data-feedback="true"></div>
<script type="module" src="/concourse/concourse.js"></script>

3. Enable private feedback.

The feedback widget accepts questions, problems, and suggestions. It carries the page revision, an optional section, and selected text you choose to include. It does not collect screenshots or browser details.

Set the optional maintainers list to exact email addresses in the backend's SITES configuration to enable the private inbox. All signed-in site members can submit feedback; only those maintainers can read it. Feedback does not automatically create an issue or send a notification.

4. Review feedback and discussions.

Open the maintainer workspace, or choose Open maintainer workspace in the feedback widget. Sign in using the publication’s managed login. Site membership alone does not grant workspace access.

The backend’s maintainers list grants private feedback access. Its independent moderators list grants discussion management. Configure exact email addresses in each list; a reviewer may have either role or both.

  1. Use Overview to open a queue by status.
  2. Apply search, status, resource, section, UTC time, and sort controls. Feedback also has a type filter. Discussion search includes replies.
  3. Open an item to see its original text, revision, and review history. Triage feedback as New, In review, or Closed.
  4. Resolve or reopen a discussion. A new reply reopens a resolved thread. If another contribution arrives during review, reload and reconcile before saving.

Original submissions remain unchanged. Review statuses do not send notifications or imply that an issue was fixed. After an uncertain save, retry the retained command before editing.

5. Verify the real journey.

Test signed-out and signed-in access on every origin. Post a comment, reload, reply, submit feedback, and verify the correct workspace tabs for each reviewer role. An interrupted save retains its draft and retry key: retry it before editing. Local tests do not qualify a deployed identity provider or a recovery procedure.

Source contracts and deployment commands are in the project documentation.
